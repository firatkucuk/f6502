Overview

PetScript is a statically typed compiled language targeting the 6502 CPU and Commodore 64. Its syntax deliberately mirrors TypeScript so that the language feels familiar while being radically constrained by 8-bit hardware. Every construct has a predictable, low-cost 6502 translation — there are no hidden allocations, no garbage collector, and no standard library.

🔬
No hidden cost
Every operator maps to one or two 6502 instructions. Nothing is free.
🗺️
Hardware is visible
VIC-II and CIA registers are first-class named fields, not magic numbers.
🧠
Memory is explicit
@zp and @addr give exact control over placement.
🔩
Escape hatch
asm {} drops to raw 6502 at any point with variable interpolation.

Hello, C64

petscript
// Border color cycles through all 16 C64 colors
program @ 0xC000 {
  loop {
    for (let c: u8 = 0; c < 16; c++) {
      VIC2.borderColor = c;
    }
  }
}

Design principles:

  1. Types reflect the machine — u8 is the atom, u16 is two atoms
  2. Every construct has a direct, predictable 6502 translation
  3. Zero-page placement is explicit and programmer-controlled
  4. No runtime, no GC, no heap — what you write is what runs
  5. The hardware is always visible; no abstraction hides memory-mapped I/O

Type System

PetScript has four primitive types and two composite forms. All types are value types packed with no padding. There are no signed integers, no floats, no strings, and no nullable types.

bool encoding: true is stored as byte value 1; false as 0. The compiler always emits canonical values — hardware registers and asm output must also write 0 or 1 when assigning to a bool variable. Comparing a bool with == true is safe; comparing with a non-canonical value like 0xFF will not match.

Variables & Constants

Variables are statically allocated at compile time. There is no stack frame for locals — every variable lives at a fixed address chosen either by the compiler or pinned explicitly by the programmer.

petscript
// Compiler-allocated — placed in RAM above the code
let count: u8 = 0;
let score: u16 = 0;

// Zero-page — @zp gives fast 2-byte absolute addressing (vs 3-byte)
// Allocates from $02 upward; the range $F8–$FF is ABI-reserved
let @zp frame:  u8 = 0;
let @zp cursor: u8 = 0;
let @zp dest:   ptr<u8> = 0x0400;   // screen RAM pointer

// Fixed address alias — no storage allocated; addr is the variable
let @addr(0xD020) borderReg: u8;
let @addr(0x0400) screen:    [u8; 1000];

// Compile-time constant — folded into immediates, no RAM used
const COLS:    u8  = 40;
const ROWS:    u8  = 25;
const SCREEN:  u16 = 0x0400;
const LOAD_AT: u16 = 0xC000;
@zp budget: Zero page is 256 bytes. The compiler allocates @zp vars from $02. Addresses $F8–$FF are reserved for the function-call ABI (u16 parameter passing). Exceeding the budget is a compile error.

KERNAL / BASIC conflict: The C64 KERNAL and BASIC ROM use much of ZP ($00–$8F and beyond). When the KERNAL is enabled (default), only approximately $02–$0F and $FB–$FE are safely free. The compiler supports execution profiles: --profile kernal-off (ZP fully available after SEI; LDA #$35; STA $01) and --profile basic-off (partial). Choose a profile matching your startup sequence to avoid clobbering KERNAL state.

Structs

Structs are value types packed sequentially with no padding. Fields are accessed via compile-time offset arithmetic — player.x resolves to the base address of player plus the field's byte offset. Structs cannot contain functions and cannot be more than one level deep in zero page.

petscript
struct Point {
  x: u8,
  y: u8,
}

struct Sprite {
  x:       u8,
  y:       u8,
  color:   u8,
  enabled: bool,   // bool is 1 byte — packed, no gap
}

// Instance in zero page — fast field access
let @zp player: Sprite = { x: 100, y: 100, color: YELLOW, enabled: true };

// Array of structs at a fixed address — 8 × 4 bytes = 32 bytes
let @addr(0xC800) enemies: [Sprite; 8];

// Field reads and writes resolve to base + offset at compile time
player.x = 120;             // STA $ZP_BASE+0
enemies[3].color = RED;     // STA $C80E  (3×4 + 2 = $C800 + 14 = $C80E)

Functions

Functions compile to subroutines with a defined calling convention. The 6502 has no hardware frame pointer, so PetScript uses registers for small argument lists and zero-page ABI slots for larger ones.

Calling convention

ScenarioHow
1 u8 paramA register
2 u8 paramsA (1st), X (2nd)
3 u8 paramsA (1st), X (2nd), Y (3rd)
4+ params or any u16Zero-page ABI slots $F8–$FF (compiler-managed)
Return u8A register
Return u16A = lo byte, Y = hi byte
Return void—
petscript
// 1 param → A; return → A
// compiles to: CMP #200 / BCC skip / LDA #200 / skip: RTS
fn clamp(val: u8): u8 {
  if (val > 200) return 200;
  return val;
}

// 2 params → A, X; return → A
// 6502 has no register-to-register ADC; compiler spills X:
//   STX $tmp; CLC; ADC $tmp; RTS
fn add(a: u8, b: u8): u8 {
  return a + b;
}

// u16 return — A=lo, Y=hi
fn screenAddr(col: u8, row: u8): u16 {
  return SCREEN + (row as u16) * 40 + col as u16;
}

// @inline — body pasted at call site, no JSR/RTS overhead
@inline fn setBorder(c: u8): void {
  VIC2.borderColor = c;
}

// 4-param — all params go through ZP ABI block $F8–$FB (no register mixing)
// caller: STA $F8; STX $F9; STY $FA; LDA color; STA $FB; JSR drawTile
fn drawTile(x: u8, y: u8, tile: u8, color: u8): void {
  // x→$F8, y→$F9, tile→$FA, color→$FB (all via ZP ABI slots)
}
Stack budget: The 6502 hardware stack is 256 bytes at $0100–$01FF. Each JSR pushes 2 bytes (return address). The compiler statically estimates call depth and warns when the budget may be exceeded. Mutual recursion is a compile error.
Re-entrancy / u16 params: Because there is no stack frame, ZP ABI slots ($F8–$FF) are global. A function receiving a u16 parameter must copy it into a function-owned ZP variable before making any nested call — otherwise the nested call's own argument setup will overwrite the in-progress slot. The compiler enforces this and emits a copy sequence automatically; do not rely on reading an ABI slot after a JSR.

Control Flow

All control flow compiles to branch instructions (BEQ, BNE, BCC, BCS) and unconditional jumps. The compiler chooses the shortest branch form when the target is within ±127 bytes, and inserts a bridging JMP otherwise.

petscript
// if / else if / else
if (lives == 0) {
  gameOver();
} else if (score > 9999) {
  displayWin();
} else {
  update();
}

// while — evaluates condition before body
while (VIC2.rasterLine != 255) {}   // busy-wait for raster line

// for — compiler tries to hold the counter in X or Y
for (let i: u8 = 0; i < 40; i++) {
  screen[i] = 0x20;   // fill with spaces
}

// Downcount — maps directly to DEX/BNE (tightest loop)
for (let i: u8 = 40; i != 0; i--) {
  screen[i - 1] = 0x20;
}

// loop — infinite; use break to exit
loop {
  update();
  render();
  if (quit) break;
}

// break and continue compile to forward/back JMP
while (idx < 64) {
  if (data[idx] == 0) break;
  if (data[idx] == 0xFF) { idx++; continue; }
  process(data[idx]);
  idx++;
}

Operators

Operators map predictably to 6502 instructions. Division and modulo are emitted as software routines and annotated with a performance note. Shift amounts must be compile-time constants; the compiler unrolls them.

u16 comparisons are not a single CMP. The compiler emits a two-step sequence: compare the high byte first, branch on that, then compare the low byte. Equality requires both bytes to match; ordered comparisons (<, >) use the high byte result unless it is equal.

Inline Assembly

asm {} blocks emit raw 6502 bytes inline. They use standard 6502 mnemonics. PetScript variables can be referenced inside the block with ${name} — the compiler resolves these to the variable's address or immediate value at link time.

petscript
// Basic block — standard 6502 mnemonics
asm {
  sei              // disable interrupts
  lda #$1b
  sta $D011        // set text mode
  cli
}

// ${name} for PetScript variables
// @zp var → its zero-page address (used as ZP operand)
// const  → its immediate value
let @zp count: u8 = 10;
const MAX: u8 = 200;

asm {
  lda ${count}     // LDA $02 (ZP address of count)
  cmp #${MAX}      // CMP #200 (immediate constant)
  bcc done
  lda #${MAX}
  sta ${count}
  done:
}

// Indirect addressing — ptr<u8> in ZP enables (zp),y
let @zp dst: ptr<u8> = 0x0400;
asm {
  lda #0x20        // space char
  ldy #0
  sta (${dst}),y   // store via ZP indirect+Y
}

// Clobber annotation — compiler will not keep live values
// in the listed registers across this block.
// Plain asm {} conservatively clobbers A, X, Y and all flags.
// List only what you actually touch to allow the compiler
// to keep the rest live.
asm clobbers(A, X, flags) {
  ldx #39
  lda #0x20
clear: sta 0x0400,x
  dex
  bpl clear
}

// Struct field reference — ${struct.field} resolves to base+offset address
let @zp player: Sprite = { x: 100, y: 100, color: YELLOW, enabled: true };
asm clobbers(A) {
  lda ${player.x}     // LDA $ZP_BASE+0 (player.x offset resolved at compile time)
  clc
  adc #4
  sta ${player.x}
}

// lo() / hi() — extract address bytes for indirect/self-modifying patterns
const TABLE: u16 = 0xCC00;
asm clobbers(A) {
  lda #lo(TABLE)      // LDA #$00  (low byte of 0xCC00)
  sta ptr_lo
  lda #hi(TABLE)      // LDA #$CC  (high byte of 0xCC00)
  sta ptr_hi
}
Rules: Labels inside asm {} are scoped to that block. ${struct.field} interpolation resolves struct field offsets at compile time and is fully supported. lo(expr) and hi(expr) extract the low and high bytes of any compile-time constant address. A plain asm {} without a clobbers() annotation is treated as clobbering A, X, Y and all flags; annotate to relax that assumption.

Hardware Blocks

A hardware block defines a memory-mapped register layout at a fixed base address. Fields are not allocated — they are compile-time aliases for base + offset. Access looks identical to struct field access but never copies any data.

All hardware block fields are implicitly volatile. The compiler never caches, reorders, or eliminates reads or writes to hardware block fields — every access emits a real LDA or STA. This is essential for memory-mapped I/O: the VIC-II, SID, and CIA chips react to every individual access. Do not use normal variables as aliases for hardware registers; only hardware block fields carry volatile semantics.

NMOS 6502 hazard: Never use INC / DEC on hardware registers — the NMOS 6502 performs a spurious intermediate write that corrupts the register. Use read-modify-write via A instead: VIC2.spriteEnable = VIC2.spriteEnable | mask.

Access modifiers

petscript
hardware VIC2_detail @ 0xD000 {
  // readonly — compiler rejects writes (e.g. read-only status register)
  readonly  lpX:         u8 @ 0x13,   // light pen X
  readonly  lpY:         u8 @ 0x14,

  // writeonly — compiler rejects reads (register has no readable state)
  writeonly irqAck:      u8 @ 0x19,   // write 1 to clear IRQ flag

  // read_to_clear — reading the register clears it as a hardware side-effect
  read_to_clear spSprCol: u8 @ 0x1E,  // sprite–sprite collision (cleared on read)
  read_to_clear spBgCol:  u8 @ 0x1F,  // sprite–bg   collision (cleared on read)

  // Separate aliases for a register that is different on read vs write
  readonly  rasterLine: u8 @ 0x12,    // current raster line (read)
  writeonly rasterIRQ:  u8 @ 0x12,    // raster compare IRQ trigger (write)
}

VIC2, CIA1, CIA2, and SID are pre-defined in every PetScript compilation unit. Programs can re-declare or extend them. The built-in color constants (BLACK, WHITE, RED … LIGHT_GREY) map to the 16 standard C64 palette values 0–15.

Program Block

The program block is the entry point — exactly one per compilation unit. The load address sets the two-byte PRG header, and execution begins at the first statement in the block.

petscript
// Machine-code entry at $C000 (default safe zone)
program @ 0xC000 {
  asm { sei }   // disable IRQs while initialising
  asm { cld }   // clear decimal mode — NMOS 6502 power-on state is undefined
  VIC2.borderColor = BLACK;
  VIC2.bgColor0 = BLACK;
  init();
  loop {
    update();
    render();
  }
}

// BASIC auto-run variant — load at $0801
// Compiler prepends the BASIC stub: 10 SYS 2062
// so typing RUN starts the program from BASIC
program @ 0x0801 {
  init();
  loop { mainLoop(); }
}

Data sections

petscript
// Binary data embedded in the PRG at a fixed address
data @addr(0x0340) {
  // Sprite data must be 63 bytes; pointer block at $07F8 holds block number
  ballSprite: [u8; 63] = [
    0b00000000, 0b11111100, 0b00000000,
    0b00000011, 0b11111111, 0b00000000,
    0b00000111, 0b11111111, 0b10000000,
    // ... 60 more bytes ...
  ];
}

// Sine lookup table for smooth animation
data @addr(0xCC00) {
  sinTab: [u8; 256] = [ 128, 131, 134, /* ... */ ];
}

// Compiler-placed data — address assigned by the linker, sits after code in PRG.
// Use when runtime address != load address (e.g. sprite data copied to $0340 at startup).
data {
  ballSprite: [u8; 63] = [
    0b00000000, 0b11111100, 0b00000000,
    // ... 60 more bytes ...
  ];
}
// initSprite() then copies ballSprite[] to ptr<u8> @zp dst = 0x0340 at runtime.
Load address vs runtime address: @addr(N) sets both the address where the data appears in the PRG binary and where it is accessed at runtime — they must be the same. If your data needs to live at an address that is not contiguous with the code (e.g. sprite block at $0340 and code at $C000), use a plain data {} block (no @addr) and copy the bytes to their runtime destination in program. A future data @load(A) @runtime(B) syntax will automate this copy in the startup routine.

Full Example — Bouncing Sprite

A complete program: one hardware sprite bouncing around the screen, synchronized to the VIC-II raster. Demonstrates structs, hardware block access, zero-page variables, and the main loop pattern.

petscript · bounce.pet
// Sprite block 13 is at runtime address $0340 ($0340 / 64 = 13)
// ballSprite bitmap lives in the PRG at a compiler-chosen address;
// initSprite() copies it to $0340 at startup.
const SP_BLOCK: u8  = 13;
const SP_PTR:   u16 = 0x07F8;   // sprite pointer 0 in screen RAM

// Zero-page state — fast access every frame
let @zp sx:    u8    = 100;
let @zp sy:    u8    = 100;
let @zp dx:    u8    = 2;
let @zp dy:    u8    = 1;
let @zp goR:   bool  = true;    // moving right?
let @zp goD:   bool  = true;    // moving down?

fn initSprite(): void {
  // @addr inside function scope is valid — aliases the fixed address, no stack allocation
  let @addr(0x07F8) ptr0: u8;
  ptr0 = SP_BLOCK;               // point sprite 0 to block 13

  VIC2.spriteEnable = 0x01;      // enable sprite 0 only
  VIC2.sprite0color = YELLOW;

  // Copy sprite bitmap from PRG payload into block 13 at $0340
  // ballSprite lives at a compiler-chosen PRG address (not $0340);
  // this loop copies it to the runtime destination.
  let @zp dst: ptr<u8> = 0x0340 as ptr<u8>;
  for (let i: u8 = 0; i < 63; i++) {
    dst[i] = ballSprite[i];
  }
}

fn moveSprite(): void {
  if (goR) {
    sx += dx;
    if (sx > 220) { goR = false; }
  } else {
    sx -= dx;
    if (sx < 24)  { goR = true; }
  }

  if (goD) {
    sy += dy;
    if (sy > 220) { goD = false; }
  } else {
    sy -= dy;
    if (sy < 50)  { goD = true; }
  }

  VIC2.sprite0x   = sx;
  VIC2.sprite0y   = sy;
  VIC2.spriteXmsb = VIC2.spriteXmsb & 0xFE; // clear MSB (X < 256)
}

// @inline with loops is valid — the compiler pastes the entire loop body inline.
// No JSR/RTS overhead; the poll runs in-place at every call site.
@inline fn waitVsync(): void {
  while (VIC2.rasterLine != 255) {}
  while (VIC2.rasterLine == 255) {}
}

Compiler

The entire compiler is a single TypeScript file with no external imports, matching the zero-dependency ethos of the f6502 emulator. Output is a raw Uint8Array: two LE header bytes followed by machine code.

1
Lexer
Hand-written character scanner; no regex library. Produces a flat token stream.
2
Parser
Recursive descent over the token stream. Produces a typed AST with source positions.
3
Type Checker
Verifies u8/u16/struct consistency, ABI compatibility, zero-page budget, and stack depth.
4
Code Generator
Walks the AST and emits a byte array with a parallel label/fixup table. Branch targets use forward fixups.
5
Linker
Resolves all label references. Patches branch offsets (±127 bytes; inserts bridging JMP otherwise). Patches absolute u16 addresses.
6
PRG Writer
Prepends the 2-byte little-endian load address. If load address is $0801, also prepends the BASIC SYS stub. Writes the final .prg.

PRG output format

binary layout
offset 0:  lo(load_address)
offset 1:  hi(load_address)
offset 2+: [zero-page init routine]   // LDA/STA pairs for @zp initializers
           [program / function code]  // main + all fn bodies
           [data sections]            // @addr data blocks, in declaration order
