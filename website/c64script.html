TypeScript for the 6502

C64Script

Write Commodore 64 programs in a language that feels familiar. C64Script compiles directly to 6502 machine code — no assembly, no linker scripts, no makefile. Just TypeScript-like syntax that becomes bytes your C64 can run.

▶ Open the Playground Try in the Demo View compiler source

Language features

Everything you need, nothing you don't

C64Script targets the 6502's constraints directly. Every feature maps cleanly to machine instructions — there is no runtime, no garbage collector, no hidden overhead.

🔤

Familiar TypeScript-like syntax

Variable declarations, typed globals, if/else, loops, functions — the structure you already know, targeting 8-bit hardware from 1982.

⚡

Zero-page annotation @zp

Mark variables @zp to place them in zero page ($00–$FF). The 6502 can address these with a single byte instead of two, making every access faster and smaller. You get 246 bytes of zero-page space ($02–$F7).

🔌

Hardware register access @addr

Pin any variable to a specific memory address. The built-in VIC2.*, SID.*, CIA1.* and CIA2.* fields use this — they are just fields bound to chip registers, not magic.

🎨

Color constants

All 16 C64 colors are built-in constants: BLACK, WHITE, RED, CYAN, PURPLE, GREEN, BLUE, YELLOW, ORANGE, BROWN, LIGHT_RED, DARK_GREY, MEDIUM_GREY, LIGHT_GREEN, LIGHT_BLUE, LIGHT_GREY. They fold to immediate values at compile time — no runtime cost.

🔁

Loops and conditionals

while, for, loop (infinite), break, continue. if / elif / else chains with full JMP-patching so every branch lands correctly.

🧩

Functions

Define reusable fn blocks with u8 parameters and a return type. Calls compile to JSR/RTS, or inline the body when marked @inline. Parameters live in fixed zero-page slots, so there is no recursion.

Examples

See it in action

rainbow-border.c64s 
// Cycle the border through all 16 C64 colours
let @zp color: u8 = 0;
let @zp ticks: u8 = 0;

program @ 0x0810 {
  loop {
    // wait for one video frame
    while (VIC2.rasterLine != 200) {}
    while (VIC2.rasterLine == 200) {}

    ticks = ticks + 1;
    if (ticks == 5) {
      ticks = 0;
      color = color + 1;
      if (color == 16) { color = 0; }
      VIC2.borderColor = color;
    }
  }
}

Use a function to keep the main loop clean. Parameters are u8 values bound to fixed zero-page slots, so a function cannot call itself:

function.c64s 
// A function without parameters, called from the main loop
let @zp shade: u8 = 0;

fn nextShade(): void {
  shade = shade + 1;
  if (shade == 16) { shade = 0; }
}

program @ 0x0810 {
  loop {
    while (VIC2.rasterLine != 200) {}
    while (VIC2.rasterLine == 200) {}
    nextShade();
    VIC2.bgColor0 = shade;
  }
}
Pro tip — variables live in zero page. Every let is allocated in zero page automatically (246 bytes in total), so reads and writes are 2-byte instructions instead of 3. const values take no memory at all: they fold into the code.

Use color constants directly — they compile to zero-cost immediates:

colors.c64s 
// Colour constants compile to immediates
program @ 0x0810 {
  VIC2.borderColor = BLUE;       // → LDA #6 ; STA $D020
  VIC2.bgColor0    = LIGHT_BLUE; // → LDA #14; STA $D021

  loop {}  // run forever
}

Type system

Types and annotations

TypeWidthRangeNotes
u8 8-bit 0 – 255 Maps to the 6502 accumulator. All arithmetic is modulo 256.
u16 16-bit 0 – 65535 Partial support — declare it and read it with lo() / hi(); arithmetic on it is incomplete.

Annotations

AnnotationEffect
(none) let x: u8 is placed in zero page for you; const X: u8 = 5 is a compile-time constant with no storage. Both accept constant expressions as initialisers.
@zp Place variable in zero page ($00–$FF). Generates shorter, faster opcodes. Max 246 bytes in total ($02–$F7) across all variables.
@addr(0x0D40) Place a data block (data @addr(0x0D40) { … }) at a fixed address. The built-in VIC2, SID, CIA1 and CIA2 hardware fields are bound to chip registers the same way.

6502 comparisons are unsigned. There are no signed integers in C64Script. 255 < 0 is false; 200 > 100 is true. Keep this in mind when writing loop conditions near the 0 / 255 boundary.

Internals

Compiler pipeline

The compiler is a clean six-stage pipeline, each stage transforming one data structure into the next. The whole thing is <1,500 lines of TypeScript.

📖 Lexer source → tokens
🌳 Parser tokens → AST
🔍 Checker validates & folds
⚙️ CodeGen emits opcodes
🔗 Linker resolves fixups
💾 PRG Writer → Uint8Array

Stage 1 — Lexer

Scans the source character-by-character and produces a flat list of typed tokens: keywords, identifiers, integer literals, operators, and punctuation. Throws LexError on unexpected characters.

Stage 2 — Parser

Consumes the token stream and builds an AST (Abstract Syntax Tree). The grammar is hand-written recursive descent — no parser generator. Throws ParseError on unexpected tokens or structural errors.

Stage 3 — Type Checker

Two-pass analysis. Pass 1 collects all function signatures and variable declarations. Pass 2 validates types, resolves @zp / @addr annotations, and folds constant variables — variables declared without an annotation whose initialiser is a literal get a constValue field, so the code generator emits an immediate mode opcode rather than a memory access. All 16 color constants are folded this way. Throws TypeError.

Stage 4 — Code Generator

Walks the checked AST and emits 6502 opcodes into a CodeBuffer. Labels and forward-jump targets are recorded as fixups — placeholder bytes that the linker patches. Zero-page allocation is tracked to avoid collisions. Throws CodeGenError for things like calling an undefined function.

Stage 5 — Linker

Iterates through all fixups and patches the placeholder bytes with the resolved addresses. Branch fixups use signed 8-bit offsets (branch8); absolute jumps use 16-bit little-endian values (abs16). Zero-page fixups use single-byte addresses.

Stage 6 — PRG Writer

Prepends the 2-byte little-endian load address (e.g. $08 $10 for address $1008) to the byte buffer. The result is a valid Commodore PRG file that F6502.player.load() or any real C64 can load directly.

API

Using the compiler from JavaScript

compile-and-run.ts 
import { compile, C64ScriptError } from 'f6502';

const source = `
  program @ 0x0810 {
    loop { VIC2.borderColor = VIC2.borderColor + 1; }
  }
`;

try {
  const prg: Uint8Array = compile(source);
  // prg is a valid .prg file (load address + machine code)
  await player.load(prg);
} catch (err) {
  if (err instanceof C64ScriptError) {
    // every compiler error carries the source position
    console.error(`${err.name} at ${err.line}:${err.col}:`, err.message);
  }
}

Error types

All of them extend C64ScriptError, which carries line and col. In a plain <script> tag the compiler is F6502.compile.

ClassWhen thrown
LexError Unexpected character, invalid number literal, unterminated comment
ParseError Unexpected token, missing semicolon, malformed expression
C64ScriptTypeError Undefined variable or function, type mismatch, write to read-only field, missing program block
CodeGenError Call to undefined function, zero-page overflow

Roadmap

Current limitations

C64Script is young. Here's what's not there yet — and why.

NO MUL / DIV

No multiplication or division

Missing native 6502 instruction

The 6502 has no multiply or divide opcode. Workarounds exist (repeated addition, shift-and-add), but C64Script doesn't generate them yet. Use bit-shifts & / | for power-of-two multiples.

NO ARRAYS

No arrays or pointers

Design in progress

Indexed addressing (e.g. LDA $C000,X) is powerful on 6502, but mapping it to a safe language construct is non-trivial. Array indexing and asm {} parse but are a compile error for now, rather than silently producing nothing.

NO STRINGS

No string literals

Screen-code encoding complexity

The C64 uses PETSCII and screen codes, not ASCII. Proper string support requires a plan for encoding and screen memory layout.

PARTIAL

u16 type is partial

16-bit operations need more work

u16 variables can be assigned, copied, incremented and read with lo() / hi(). Arithmetic and comparison on them is a compile error until 16-bit support lands; use u8 for that.

CONST ADDR

poke() needs a constant address

No computed addresses yet

poke(0x0400 + 495, value) works and value can be any expression, but the address must be known at compile time. A computed address is a compile error.

NO RECURSION

Functions cannot call themselves

No stack frame

Parameters and locals live at fixed zero-page addresses, so a function that calls itself, directly or through another function, is a compile error. &&, ||, *, / and shifts on variables are compile errors too, and the right-hand side of + - & | ^ and of comparisons must be a literal, a variable or a hardware register.

Contributions welcome. The compiler is <1,500 lines of TypeScript with a comprehensive test suite. If you want to add arrays, multiplication, or more hardware registers, the source is on GitHub.
