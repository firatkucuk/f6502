The Commodore 64 (1982)

On January 7, 1982, Jack Tramiel strode onto the floor of the Consumer Electronics Show in Las Vegas and announced a machine that would outsell every personal computer in history. The Commodore 64 shipped with 64 kilobytes of RAM, a dedicated sound chip, and a hardware sprite engine — at a retail price of $595.

Tramiel's philosophy was captured in a single memorable phrase: "Computers for the masses, not the classes." Within a year the price had dropped below $200. By the time production ended in 1994, Commodore had sold an estimated 17 million units — the best-selling single computer model ever manufactured.

The MOS 6502 (1975)

The story of the 6502 begins at Motorola. Chuck Peddle was a chip designer who believed the industry had it backwards — microprocessors cost hundreds of dollars when they should cost tens. When Motorola declined to pursue this vision, Peddle and a team of colleagues left for MOS Technology, a small semiconductor house in Norristown, Pennsylvania.

They designed the MOS 6501 and 6502 in nine months. At the 1975 WESCON electronics show, MOS sold the 6502 for $25 — at a time when the Intel 8080 cost $179 and the Motorola 6800 cost $175. The audience thought it was a mistake. It wasn't.

Apple Computer built the Apple I and Apple II around the 6502. Atari used it for the 2600 and 800. Acorn chose it for the BBC Micro. Nintendo built the Famicom (NES) on a 6502 variant. The Commodore 64 used the 6510, a slightly modified version with an onboard I/O port. In total, more than one billion 6502-family chips have been manufactured.

6502 in C64: The Commodore 64 uses the MOS 6510, a 6502 variant with a built-in 8-bit I/O port at addresses $00 (direction register) and $01 (data register). The port controls ROM banking — switching between BASIC, KERNAL, character ROM and RAM — and the tape interface.

6502 CPU Architecture

The 6502 is an 8-bit CPU with a 16-bit address bus, giving it access to 64KB of memory. The design is refreshingly lean: six registers, 56 distinct instructions, and 13 addressing modes. Every bus access — read or write — takes exactly one clock cycle, which makes it possible to implement cycle-accurate emulation without counting sub-cycle state.

Registers

A — Accumulator 8-bit Primary arithmetic register. Most operations use A as their target.
X — Index X 8-bit Index register. Used for indexed addressing and as a general scratch register.
Y — Index Y 8-bit Index register. Same role as X; some instructions use Y when X is unavailable.
PC — Program Counter 16-bit Points to the next instruction to execute. Initialized from the reset vector at $FFFC.
SP — Stack Pointer 8-bit Points into page 1 ($0100–$01FF). The hardware stack. Grows downward.
P — Status 8-bit Flags: N V — B D I Z C. Carry, Zero, IRQ disable, BCD, Break, oVerflow, Negative.

Addressing modes

The 6502's power comes from its orthogonal addressing modes. The same instruction — say, LDA (Load Accumulator) — can address an immediate value, a zero-page byte, an absolute address, or an indexed/indirect variant, each encoded as a different opcode.

The zero page trick: Addresses $0000–$00FF are "zero page". Accessing them takes one fewer cycle than a full 16-bit address and uses a 1-byte operand instead of 2. C64 programmers cram their hottest variables into zero page. C64Script's @zp annotation does this automatically.

Interrupts and vectors

The 6502 has three hardware vectors: RESET ($FFFC–$FFFD, read at startup and after a hardware reset), IRQ ($FFFE–$FFFF, triggered by the CIAs and VIC-II raster), and NMI ($FFFA–$FFFB, non-maskable, used by the C64's RESTORE key). The C64 KERNAL ROM installs handlers at all three.

VIC-II Graphics Chip (MOS 6567/6569)

The Video Interface Controller II is the graphics heart of the C64. Introduced in 1982 alongside the machine, it handles character display, bitmap graphics, hardware sprites, smooth scrolling, raster interrupts, and the complex timing interactions that made the C64 demo scene possible.

Hardware sprites

The VIC-II provides 8 hardware sprites, each 24×21 pixels. Sprites have independent positions (X/Y registers), colour, and can be doubled in size. The chip handles sprite-to-background and sprite-to-sprite collision detection in hardware — reading registers $D01E and $D01F tells you which sprites collided since the last read.

Badlines and CPU stalling

This is where the C64's timing gets interesting. Every eighth raster line is a "badline" — the VIC-II needs to fetch a row of character pointers from shared memory. During a badline, VIC-II asserts the BA (Bus Available) signal low, which stalls the CPU for up to 40 cycles. Any program doing timing-critical work must account for badlines, or graphics will glitch.

f6502 implements cycle-exact BA stalling. The emulated CPU checks BA before every bus read, and if BA is low (VIC-II is stealing the bus), it idles rather than proceeding. This is how demo programmers pull off effects that seem impossible on a 1 MHz CPU.

Raster interrupts

The VIC-II can trigger an IRQ when the raster beam reaches any specified line. This is the foundation of the C64 demo scene's most iconic tricks: split-screen effects, mid-frame colour changes, hardware sprites repositioned between frames. By changing the screen layout in the IRQ handler precisely timed to the raster beam, programmers can display more than the hardware nominally supports simultaneously.

SID Sound Chip (MOS 6581 / 8580)

The Sound Interface Device is, arguably, the most beloved chip ever manufactured by MOS Technology. Designed by Bob Yannes (who later co-founded Ensoniq), the SID was wildly overpowered for its era: a fully programmable analog synthesiser on a single chip, stuffed into a home computer that cost less than a console.

The SID has three fully independent voices. Each voice can produce four waveforms, has a complete ADSR (Attack Decay Sustain Release) volume envelope, and feeds into a shared resonant low-pass/high-pass/band-pass filter. Professional musicians still compose for it today.

4 Waveforms each
ADSR Per-voice envelope
3-mode Resonant filter
~1 MHz Clock rate

The waveforms

Each voice oscillator can produce four basic waveforms, or combinations of them (which create unusual timbres — a quirk of the analog hardware):

  • Triangle — smooth, low in harmonics, flute-like
  • Sawtooth — rich in harmonics, synth-string character
  • Pulse (variable) — the pulse width register ($D402/$D403) controls the duty cycle from a thin click to a square wave; sweeping it gives the classic "PWM" sound
  • Noise — a 23-bit linear feedback shift register producing pseudo-random values; used for percussion and sound effects

ADSR envelope

Each voice has a four-stage amplitude envelope. Attack ramps the volume from zero to maximum; Decay falls to the Sustain level, which holds as long as the gate bit is set; Release falls back to zero when the gate is cleared. The 6581 has a well-documented bug where the envelope counter can overshoot on fast release — f6502 replicates it.

6581 vs 8580

The original 6581 runs on 12V and uses analog circuits that filter with a notoriously non-linear curve — the basis of much SID "warmth". The revised 8580 (1987) runs on 9V, has a cleaner filter response, and a slightly different noise waveform. Many compositions sound noticeably different on each revision. f6502 lets you select the model with audio: { model: '6581' }.

AudioWorklet: f6502 outputs SID audio via the Web Audio API's AudioWorklet. The SID runs in the main thread, samples are buffered, and the worklet drains the buffer in the audio processing thread. This avoids the crackling that comes from ScriptProcessor and tolerates frame timing jitter.

C64 Memory Map

The C64's 64KB address space is divided into regions that can be banked in and out via the I/O port at $01. In the default configuration (LORAM=1, HIRAM=1, CHAREN=1):

$0000–$00FF Zero Page — fast RAM used by BASIC and OS 256 B
$0100–$01FF Stack — 6502 hardware stack (page 1) 256 B
$0200–$02FF BASIC I/O buffers — keyboard buffer, etc. 256 B
$0801–$9FFF BASIC program RAM — where your BASIC lines live ~38 KB
$A000–$BFFF BASIC ROM (banked) — the BASIC interpreter 8 KB
$C000–$CFFF RAM — available to machine code programs 4 KB
$D000–$D3FF VIC-II registers — graphics, sprites, raster 1 KB
$D400–$D7FF SID registers — voices, filter, ADSR 1 KB
$D800–$DBFF Colour RAM — one nibble per character cell 1 KB
$DC00–$DCFF CIA 1 — keyboard matrix, joystick, timers 256 B
$DD00–$DDFF CIA 2 — serial bus, VIC bank select, timers 256 B
$E000–$FFFF KERNAL ROM (banked) — OS routines, interrupt handlers 8 KB

Our Emulator Design

f6502 is a clean-room implementation — no code from any prior emulator. Every component was designed from hardware datasheets, the C64 programmer's reference, and extensive cross-checking against VICE output. The guiding principle: prefer correctness over performance, but make it fast enough to run in a browser at full speed on a mid-range laptop.

The bus abstraction

At the core is a minimal bus interface:

src/core/bus.ts 
export interface Bus {
  read(addr: number): number;
  write(addr: number, value: number): void;
}

Every bus access — whether it comes from the 6502 CPU, the VIC-II DMA, or a test — goes through this interface. The C64's memory controller implements it, routing reads and writes to the right ROM, RAM, or I/O region based on the current bank state.

Cycle accuracy

The 6502 specifies a precise number of cycles for every instruction. f6502 counts cycles as it executes each instruction and calls the VIC-II's tick() method once per CPU cycle. VIC-II maintains its own cycle counter to track which dot it is currently generating. This tight coupling is what makes raster effects work correctly.

When VIC-II needs the bus for DMA (character fetch or sprite data), it asserts BA low. The CPU implementation checks BA before each read; if low, it stalls by incrementing the cycle count without advancing the program counter. This is exactly what the real hardware does.

VIC-II timing in TypeScript

src/machine/vic.ts (simplified) 
tick(): void {
  const dot = this.dot++;
  const line = this.raster;
  const x = dot * 8;

  // Badline: VIC steals bus for character fetch
  if (this.isBadLine(line, dot)) {
    this.ba = false;
    this.fetchRow(line);
  }

  // Sprite DMA: 2 cycles per sprite on sprite lines
  if (this.spriteActive(line, dot)) {
    this.ba = false;
  }

  renderPixels(line, x); // 8 pixels per cycle
}

SID synthesis

The SID emulation runs at the CPU clock rate (~1 MHz). Each clock, every voice's oscillator phase accumulator is advanced. At the audio sample rate (44100 Hz, configurable), the oscillator output is read, the ADSR envelope is applied, and the combined voices are fed through the filter model.

The 6581 filter is particularly hard to emulate — it is a four-pole analog filter with a non-linear resonance curve that varies between chips. f6502 uses a documented approximation of the 6581 filter based on measurements from real hardware.

The code generator emits 6502 instructions directly as bytes into a CodeBuffer. Branch targets are emitted as fixups — placeholders that the linker resolves once all code is generated and every label has a known address. This is how standard assemblers work.

Testing & Verification

Emulator correctness is hard to guarantee with unit tests alone. f6502 uses three layers of testing:

Unit and machine tests

Over 600 tests covering individual 6502 instructions, the VIC-II timing logic, SID envelope behaviour, CIA registers, keyboard matrix, and the browser player. These run on every commit via Vitest.

Klaus Dormann functional test

The Klaus Dormann functional test is the gold standard for 6502 correctness. It is a 64KB program that exercises every legal opcode and addressing mode, trapping the CPU in an infinite loop if any test fails. f6502 runs the full test to completion.

VICE conformance tests

VIC-II accuracy is checked against reference screenshots captured from VICE, the most accurate C64 emulator. The SID is verified against VICE's SID test programs — self-checking programs that read back the chip's state and fail if the emulation diverges. This catches subtle timing interactions that unit tests cannot.

Open source: f6502 is published under the Apache 2.0 licence. ROMs are not included — download the free OpenROMs or use your own. Run npm run fetch-test-data to download everything needed for conformance testing.
